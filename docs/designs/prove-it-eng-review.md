## Scope challenge: what already exists
- `passport.verify_portable()` (passport.py:90) and `scripts/verify_passport.py` verify a submitted package. Reuse, do not rewrite.
- `tests/interop/test_hardening.py:248` already tampers four ways (content, hash, version, missing). These become the regression base.
- Two export call sites call `passport.portable()`: interop.py:659 and onehealth.py:474. Signing therefore belongs inside `portable()`.
- Ed25519 is available (`cryptography` 46.0.6), only transitively through `python-jose[cryptography]` (pyproject.toml:21).
Complexity check: about 10 files touched (backend 4, frontend 3, infra 2, docs 1). Acceptable; no new service or table.

## Architecture
```
 Verify stage panel (frontend/src/journey/cards.tsx)
        | edits a throwaway copy of the exported package
        v
 POST /api/v1/interop/passport/verify   (reviewer/admin, <=1 MB, stateless)
        v
 passport.verify_portable(package)  --> hash chain + manifest      (exists)
        +  passport.verify_signature(package, public_key)           (NEW)
        +  passport.diff_manifest(record)  -> names changed artifact (NEW)

 export: interop.passport_export / onehealth.export_passport
        v
 passport.portable(record, **artifacts)  --> signs {object_id, version, head, hash_manifest}   (NEW, in ONE place)
        key: settings.PASSPORT_SIGNING_KEY (env; k8s Secret; .env.example placeholder)
```
Signed message must cover `object_id + record version + head hash + hash_manifest`, never the head alone (replay).
New field `signature: {alg:"ed25519", key_id, value}`; `key_id` = first 16 hex of SHA-256 of the public key.

## Findings
| # | Sev | Conf | Finding | Fix |
|---|---|---|---|---|
| 1 | P1 | 9/10 | Signing in either export caller would leave the other unsigned (two call sites) | Sign inside `portable()` only |
| 2 | P1 | 8/10 | `verify()` returns only a status, so the panel cannot say which artifact changed | Add `diff_manifest(record)` comparing `chain[-1].artifacts` to `manifest(data)` |
| 3 | P1 | 9/10 | Existing clusters already have `clinicase-secrets`; `ensure_secret` (cluster.py) never adds new keys | Add an idempotent "add missing keys" step; never rotate existing values |
| 4 | P2 | 8/10 | `cryptography` is only a transitive dependency | Pin it explicitly in pyproject.toml |
| 5 | P2 | 7/10 | No request-size cap exists on JSON bodies; verify endpoint accepts attacker-sized input | Check `Content-Length`, return 413 above 1 MB |
| 6 | P2 | 7/10 | Legacy and unsigned packages would read as failures | Status `UNSIGNED` (hash-valid) is distinct from `SIGNATURE_INVALID` |
| 7 | P3 | 6/10 | Signature-failure details could leak exception text (the PR #5 CodeQL lesson) | Fixed status strings only |

Regression rule: the existing four tamper modes must keep passing unchanged.

## Performance
Hashing a passport is milliseconds; Ed25519 sign/verify is microseconds. No concern up to the 1 MB cap.
