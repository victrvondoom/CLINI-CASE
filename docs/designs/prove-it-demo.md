# Design: "Prove It" — a judge-driven tamper test for the Track 7 demo

## Problem Statement
CLINI-CASE has a complete 10-stage evidence journey, but a judge on a standards track cannot verify any of its
claims. "17/17 fields preserved" comes from the team's own System B and validator. The demo needs one moment
a judge can check with their own hands.

## What Makes This Cool
System B rewrites every resource ID, yet the Evidence Passport hash chain still proves nothing was altered. A
judge edits one value in the returned Bundle and watches two things react differently: the semantic round trip
flags the changed field, and the passport chain reports the exact break. Tamper-evidence becomes visible, not narrated.

## Constraints
- 4-minute demo; synthetic data only; the plain launcher must work (Kubernetes is a backup clip).
- No new backend workflow logic; reuse validate, return and passport verification.
- The generic-arsenic reviewer gate must stay intact.

## Premises (all agreed)
1. Standards judges reward verifiable interoperability evidence over feature breadth.
2. The biggest credibility gap is that System B and the validator are self-run, not third-party.
3. A live, judge-driven tamper test beats a narrated 10-stage walkthrough.
4. The oncology/twin platform is context only, never the subject of the demo.

## Approaches Considered
- **A. Prove It tamper panel (chosen).** Effort S, risk low. Tamper panel in the Verify stage using existing endpoints.
- **B. A plus third-party FHIR server and real HL7 validator output.** Effort M, risk medium. Rejected for now: depends on
  external uptime during the demo; keep as the follow-up that closes the credibility gap.
- **C. Offline verifiable receipt and public verifier page.** Effort M, risk low. Deferred: second artifact to explain in 4 minutes.

## Recommended Approach
Approach A. In the Verify stage, add a "Tamper test" panel: pick one field of the returned Bundle, change it, and
re-verify without mutating the stored job. Show side by side (1) the semantic round-trip result naming the changed
field and (2) the Passport integrity result. Use a throwaway copy; never write the tampered bundle to storage.

## Open Questions
- Does the passport verify a submitted bundle, or only the stored chain? If only the chain, the panel should tamper
  with a copy of the exported Passport JSON instead of the Bundle.
- Which field makes the clearest demo (value, unit, or analyte)?

## Success Criteria
- A judge changes one value and sees a failing check within 2 seconds, with the field named.
- The stored job and passport remain unchanged afterward (tested).
- Works on the plain launcher with no Docker.

## Distribution Plan
Existing web deployment covers this; ships in the current frontend/backend images.
